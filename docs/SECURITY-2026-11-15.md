# PLUJ security hardening, 15 Nov 2026

The 19 items asked for, what was done, and what is left. An independent
review of the code and the live database came first; every hole it found is
listed under the item it belongs to. Every database fix was then attacked
for real (signed in as a host and as a vendor) with
`sql/tests/2026-11-15-attack-tests.sql`. Every attack was refused.

| # | Item | Status |
|---|---|---|
| 1 | Protect admin routes | Done. Every admin action is a database function that checks `admin_users` itself. The admin screens are only views over those functions. `admin_delete_account` no longer trusts metadata a user can edit (`sql/2026-11-15-admin-delete-check.sql`, run 16 Nov) |
| 2 | Permissions enforced on the server | Done. Holes fixed in the database: a host could make themselves an **approved vendor**; anyone could open a fake "PLUJ Support" thread; a booking could be created already **confirmed** with any price; a host could move the event date while cancelling to dodge the late fee; cancelled bookings could be revived; reviews could be re-pointed or hidden; fake system notifications; editing one's own email or verified flags; deleting an account with live, paid bookings |
| 3 | Row-level security | Done. On every table (13 have RLS with no policies on purpose: server-only). Narrowed: calendars only for public vendors, storage file listings only for the owner. Names of people you deal with come from `party_names()`. The broad "counterparty can read my profile row" policy is switched off (done after the new site went live) |
| 4 | Verify email and phone | Email: required by Supabase Auth, done. Phone: not verified, by decision (16 Nov): it needs a paid text-message service; revisit before launch |
| 5 | Hash passwords securely | Done by Supabase Auth (bcrypt). Leaked-password check on, minimum 12 characters with 4 kinds |
| 6 | Auth tokens out of localStorage | Done. The refresh token (the 7-day key) is in an HttpOnly, Secure, SameSite=Strict `__Host-` cookie set by `api/session.js`. The hour-long access token stays in memory. localStorage keeps only who is signed in. Sessions saved before this move over on their own. Links carrying a session in the address no longer sign anyone in |
| 7 | API secrets server side | Checked. The browser bundle holds only public values: the Supabase address and anon key, and the Turnstile site key. (There is no Google Maps key: Vercel has none set, so address suggestions use the free OpenStreetMap service. If one is ever added, restrict it to pluj.us in Google Cloud.) CI fails the build if a secret-looking key appears in it |
| 8 | .env files off GitHub | Checked. `.gitignore` has `.env*`, and no .env file was ever committed (full history searched). GitHub secret scanning and push protection are on |
| 9 | No secrets in logs | Done. Error reports are scrubbed of tokens, keys, emails and query strings before they are stored or emailed. Diagnostic browser logs are off in production |
| 10 | Parameterized SQL | Checked. The site builds no SQL; it uses the Supabase API, which encodes every value, and database functions with typed parameters. The few database functions that build SQL quote only internal table names (`%I`), never anything a person typed |
| 11 | Validate form inputs | Done. Length and value limits are enforced in the database on every user-written table, which is what counts; the forms check the main fields too. Insert times now always come from the database clock, so per-account limits cannot be dodged by backdating |
| 12 | Block XSS | Done. The Content-Security-Policy forbids inline scripts and event handlers and limits script sources to the site, Google Maps and Turnstile. React escapes all text, nothing uses raw HTML, and emails escape every value. A browser test injects a script and checks it is blocked |
| 13 | Validate uploads, malware | Done: only vendors upload, only into their own folder, at most 300 files. In the browser each photo is checked by its real bytes and redrawn as a clean JPEG (no hidden data, no GPS). The bucket accepts only JPEG, PNG or WebP up to 4 MB. A scan every 10 minutes removes anything that is not a real picture. Not antivirus: that needs a paid outside service. **Incident:** the scan's first version removed one real photo (Arepas 713's profile photo); fixed within minutes; that photo needs uploading again |
| 14 | Verify webhook signatures | Checked live 16 Nov: an unsigned and a forged Stripe event were both refused ("bad signature"). Stripe signatures are verified (HMAC, 5-minute window, constant-time compare). Added, deployed at payments go-live: the payment must be on the booking's vendor account, for that booking, in full |
| 15 | Rate limit requests | Done where it is ours: Supabase Auth limits (30 sign-ups or log-ins per 5 minutes per IP, 1800 token refreshes, 30 code checks, 100 emails an hour) plus CAPTCHA on sign-up, log-in and reset; per-IP limits on every `api/` route; per-account caps on bookings, messages, reviews, listings and recaps; Vercel bot protection (a script hitting the site gets a challenge, checked 16 Nov). Gap: Supabase's own data API has no per-IP limit on this plan. Since item 6, token refreshes come from Vercel's servers rather than each visitor, so the token-refresh limit was raised from 150 to 1800 per 5 minutes on 16 Nov |
| 16 | Tighten CORS | Done. `api/` routes refuse other sites' pages. The payments function answers only www.pluj.us in the code; the live copy still answers any site until it is redeployed at payments go-live, but it refuses every request without a PLUJ login (checked 16 Nov). Supabase's API allows any origin by design and relies on login and RLS |
| 17 | Production debugging off | Done. No source maps, no debug logs, no debug endpoints, and CI checks the build |
| 18 | Patch vulnerable dependencies | Done. CI fails on known high or critical vulnerabilities in what ships. Dependabot opens one grouped pull request a week; Dependabot alerts, security updates and malware alerts on since 16 Nov. The first scan found 15 alerts, all in build and test tools; all 15 fixed on 16 Nov (0 open) |
| 19 | Claude security review | Set up, **on request only** (decided 16 Nov: no automatic paid runs). Add the label `security-review` to a pull request and Anthropic's reviewer reads it and comments; adding the label again reviews the newest code. Paid per review from the Anthropic Console credit. Tested 16 Nov on PR #16: reviewed in full, 0 findings. The job fails visibly if Claude cannot run (for example, no credit) |

## Re-check, 16 Nov 2026

Everything above was checked again on the live site, database and GitHub:

- **Attacks:** `sql/tests/2026-11-15-attack-tests.sql` plus 10 admin-only
  actions tried as a host: all 30 refused.
- **Normal use:** `sql/tests/2026-11-16-operations-tests.sql`: sign-up (host,
  vendor; under-18 refused; asking to be admin gives a normal account; refused
  while the site is private), confirming email, booking request, accept,
  cancel, chat, favorites, calendar, photo upload, pausing and returning,
  admin list, messages and support threads: all work.
- **Live site in Chrome:** home, categories, a vendor page with photos, Build
  my event, all admin tabs, notifications: no errors. Log out cleared the
  sign-in and the cookie; a fresh log-in and a reload kept the sign-in with
  nothing secret in browser storage. The sign-up form opens and checks its
  fields. Security headers present (CSP, HSTS 2 years, nosniff, frame and
  referrer rules); no source maps; no secret keys in the site's code.
- **Database:** RLS on all 36 tables; all 6 passwords bcrypt-hashed; no secrets
  in the error log; the upload scan has run every 10 minutes since 15 Nov.

Possible next step: two-step login (an authenticator app) for the admin
accounts. Supabase supports it, but the site has no screen for the second
step yet, so it is a small project, not a switch.
